# Decisions

One line each. Newest at the bottom.

- 2026-10-15: Docker dropped from v1. Install is `uv` + Ollama + a launchd/systemd service. Reason: less memory on the client's Mac, one less thing to install, and the desktop app (v1.5) needs the same shape anyway.
- 2026-10-15: Dashboard is Vite + React, not Next.js. Reason: a plain static build served by FastAPI, no Node at runtime.
- 2026-10-15: Google is called through our own thin REST client over `homer_net`, not `google-api-python-client`. Reason: the official library brings its own HTTP stack and would bypass the allowlist.
- 2026-10-15: Private repo under `Syed-Hamza10`, proprietary license. Reason: the code is the product; the demo video and case study are the public portfolio.
- 2026-10-16: Model tags verified on ollama.com: `qwen3.5:9b` (Q4_K_M, 6.6 GB) and `qwen3.5:4b-q8_0` (5.2 GB).
- 2026-10-16: Spike on M3 Pro 18 GB, `qwen3.5:9b`, 16k context: 27–32 tok/s, first token <1 s warm, ~10 s cold load, 7.7 GB resident / 8.7 GB peak, tool-call round trip 6 s. 9B confirmed as the supported tier.
- 2026-10-16: Thinking is turned off with `reasoning_effort: "none"` on Ollama's OpenAI-compatible API (Pydantic AI `thinking=False` sends exactly this). `think: false` is ignored on that API, and the default thinks for 4–6 minutes per answer. Reason: measured in the spike.
- 2026-10-16: Ollama runs with `OLLAMA_CONTEXT_LENGTH=16384` in its service environment; the OpenAI-compatible API cannot set context per request.
- 2026-10-16: Build backend is `hatchling` for every package. Reason: plan was silent; it is the uv default and needs no config.
- 2026-10-16: Thinking is turned off with `openai_reasoning_effort="none"` in the model settings, not `thinking=False`. Reason: pydantic-ai 2.57's Qwen3.5 profile has `supports_thinking=False`, so `thinking=False` is silently dropped (verified: no `reasoning_effort` in the request, 2k thinking tokens); the explicit setting reaches Ollama.
- 2026-10-16: The agent uses `@agent.instructions`, not `@agent.system_prompt`. Reason: instructions are re-rendered on every run (current time stays fresh) and are not stored in message history.
- 2026-10-16: `homer_net` stays on legacy `httpx`; pydantic-ai 2.57 warns that `httpx.AsyncClient` providers are deprecated in favour of `httpx2`. The warning is filtered in pytest. Reason: works today; moving the net package to httpx2 is a separate step once the API settles.
- 2026-10-16: Hardware tier is detected at startup (`platform.hardware_tier`) and picks the model tag from the manifest; no override setting yet. Reason: the Settings page (step 5) owns model choice.
- 2026-10-16: `CORSMiddleware` with `own_origins` and credentials is on, so the Vite dev server (`EXTRA_ORIGINS`) can call the API with the cookie. Reason: needed for `make dev`; harmless in production where the dashboard is same-origin.
- 2026-10-16: pytest runs with `--import-mode=importlib`. Reason: `packages/net/tests` and `packages/core/tests` are both named `tests`; the default mode cannot import two packages with the same name.
- 2026-10-16: `httpx` is allowed under `packages/*/tests/**` (ruff per-file-ignore for TID251). Reason: the e2e suite talks to the real server over real HTTP; production code still goes through `homer_net` only.
- 2026-10-16: `test_login_rules` starts its own server process instead of using the session one. Reason: the login limiter is in-process state that blocks every login for 60 s once tripped, which would stall the chat and browser tests.
- 2026-10-16: e2e tests are moved to the end of the collection and browser tests (anything using `page`) to the very end, by `pytest_collection_modifyitems` in the repo-root `conftest.py`. Reason: pytest-playwright's sync API keeps an asyncio loop running for the rest of the session, and pytest-asyncio tests that run after it fail with "cannot be called from a running event loop"; the hook moved out of `packages/core/tests/e2e/` once `packages/mcp_search` gained its own asyncio e2e tests.
- 2026-10-16: `ddgs` removed; `web_search` is our own ~40-line DuckDuckGo HTML client over `homer_net`, so the allowlist has no exceptions. `web_news` dropped from v1 (needs a token handshake, low value).
- 2026-10-16: `fetch_page` refuses every address that is not `ip.is_global`, not just private, loopback, link-local and reserved. Reason: one check that is a superset (adds multicast, unspecified and the 100.64/10 shared range).
- 2026-10-16: In the search server the rate gate runs before URL validation, and error results are never cached. Reason: a bogus URL costs one second at most, and caching a transient DuckDuckGo failure for an hour would hide a working search.
- 2026-10-16: Search results carry `title` and `snippet` wrapped in `<untrusted>` individually and the `url` bare. Reason: the model must pass the URL to `fetch_page` verbatim; everything else is page content.
- 2026-10-16: `parse_datetime` resolves "next <weekday>" itself to the date 7 to 13 days ahead (that weekday in the following week) and hands `dateparser` the ISO date in place of the phrase. Reason: `dateparser` 1.4 returns `None` for "next friday", and stripping "next" would turn "next friday" said on a Thursday into tomorrow.
- 2026-10-16: `parse_datetime(text, timezone, now=None)` takes an optional `now` and both system tools return objects (`{iso, weekday}`, `{iso}` or `{error}`) rather than a bare string or `None`. Reason: `now` makes the tests deterministic and the agent can pass the run's clock; an error object tells the model what went wrong.
- 2026-10-16: `packages/mcp_*/tests` have no `conftest.py` and unique module basenames (`test_search_server.py`, `test_system_server.py`). Reason: even with `--import-mode=importlib`, pytest names them `tests.<module>`, so a second `tests/conftest.py` or `tests/test_server.py` collides with the core one.
- 2026-10-16: `packages/eval` is the `homer-eval` distribution and holds only `homer_sim` for now. Reason: the plan's `eval/sim/`; tasks and the runner arrive in step 5.
- 2026-10-16: The simulator also serves `users/me/profile`, `drafts/{id}` and `events/{id}` (GET), beyond the contract's endpoint list. Reason: real Google endpoints the server needs for a first cursor, send previews and update/delete previews.
- 2026-10-16: The simulator accepts one fixed access token (`sim-access-token`) plus tokens it issued from `/token`; anything else is 401. Reason: this is what Google does, and it lets the 401-then-refresh path be tested for real.
- 2026-10-16: Simulator calendar times are UTC and events sit on the current week's Monday to Friday. Reason: deterministic tests on any day the suite runs.
- 2026-10-16: The google token file uses google-auth's `Credentials.to_json()` keys (`token`, `refresh_token`, `client_id`, `client_secret`, ...). Reason: it is what the one-time consent flow produces; the server reads it and rewrites only `token` on refresh.
- 2026-10-16: `google-auth-oauthlib` is used only inside `homer-mcp-google-setup`; its own HTTP stack performs the one-time consent exchange. Reason: the plan allows it for setup; every runtime call including refresh goes through `homer_net`.
- 2026-10-16: Neutral mail objects keep `id` and `thread_id` at the top level; Gmail extras (`label_ids`, `history_id`, `internal_date`, `message_id_header`) live under `metadata`. Reason: the ids are the handles other tools take as arguments.
- 2026-10-16: `mail_label` creates a label that does not exist yet when asked to add it. Reason: step 4 triage needs labels to appear in Gmail without a separate tool.
- 2026-10-16: `cal_find_free_slots` proposes one slot per free gap (earliest start), weekdays only, working hours read in the timezone of `start`. Reason: three proposals spread over the day are more useful than three back-to-back ones.
- 2026-10-16: The allowlist refusal test runs at the `GoogleClient` layer against the real simulator, and a second test asserts the MCP server only ever contacted the simulator host. Reason: the server's allowlist is built from the same env values as its targets, so a refusal cannot be reached through MCP by design.
- 2026-10-16: `packages/eval/tests` and `packages/mcp_google/tests` have no `__init__.py`. Reason: under `--import-mode=importlib`, a `tests/__init__.py` makes every `tests/conftest.py` import as `tests.conftest`, and pytest refuses to register the second one.
- 2026-10-16: `remind(text, when_iso)` is a core-native tool writing the `reminders` table, not a system-server tool. Reason: the scheduler and the Today page own reminders; the server only parses dates.
- 2026-10-16: Tables are `approvals` and `reminders` (plural, as in plan §8.1), not the contract's singular `approval`. Reason: every existing table is plural.
- 2026-10-16: `health` is hidden from the model together with `execute`. Reason: every server has one, so the names collide in the combined toolset, and the model has no use for it.
- 2026-10-16: The toolset classifier is a second `Agent` on the same model, run non-streamed; its tokens are added to the chat's `done` totals and the token counter, with one `requests` increment per chat.
- 2026-10-16: MCP toolsets use `tool_error_behavior="failed"`. Reason: the model sees a tool error once as a result instead of a retry loop; for `execute`, a `ToolFailed` is a clear failure (`failed`) and anything else (timeout, transport) is `unknown`.
- 2026-10-16: Approvals expire lazily: `expire_stale` runs inside `list_pending`, `approve` and `reject`. Reason: no scheduler until step 4; the state is still correct whenever it is read.
- 2026-10-16: A tier-2 action (`mail_label`, `mail_archive`) proposed after `<untrusted>` content is turned into an approval by the core and later run through the same server `execute(action, payload)`. Assumes the google server's `execute` accepts those two actions.
- 2026-10-16: Chat `Deps` carries the DB session and user id. Reason: `remind` and the approval gate write rows during a run.
- 2026-10-16: `/remind <text>` runs the agent with the `system` toolset and the prompt "Set a reminder: <text>", skipping classification. `/reject N` exists next to `/approve N`.
- 2026-10-16: Unit tests use `TestModel(call_tools=[])`. Reason: the default calls every visible tool on the first turn.
- 2026-10-16: Full `fastmcp` (server extra) is a core dev dependency only; runtime stays on `fastmcp-slim` from `pydantic-ai-slim[mcp]`. Reason: the stand-in MCP servers in `tests/fake_servers/` need the server side.
- 2026-10-16: e2e starts the server from the venv's own `homer` binary, not `uv run`. Reason: `uv run` puts the venv bin first on PATH, which would shadow the stand-in `homer-mcp-google` once a real one is installed; the approval e2e must stay deterministic.
- 2026-10-16: `/api/health` carries `servers: {google, search, system: ok|down}` (running = started over stdio and listed its tools). Reason: the real-stack e2e needs to prove the three servers are up, and the doctor and Settings page will want it.
- 2026-10-16: `homer-core` lists the three MCP server packages and `homer-eval` as dev dependencies. Reason: a fast unit test starts the real servers in-process to check every curated toolset name against the tools they actually expose, and the e2e suite needs `homer-sim`.
- 2026-10-16: The real-stack e2e writes its own seed: the default seed plus one event on tomorrow's date. Reason: the seed's events sit on this week's weekdays, so "what is on my calendar tomorrow" would have nothing to find on a Friday or Saturday.
- 2026-10-16: The browser e2e on the real stack creates its pending approval by posting a draft to the simulator and inserting the approval row, not through the model. Reason: the page test checks the UI and the real `execute` path; the model's behaviour is covered by the HTTP tests in the same module.
- 2026-10-16: The simulator gained Gmail `messages` insert (with `internalDateSource=dateHeader`) and `messages/{id}/trash`, beyond the contract's list. Reason: the demo seed script inserts dated mail and wipes it through the same REST calls it makes to Google.
- 2026-10-16: `GoogleClient` takes an optional `log` callable; the seed script passes `no_log`. Reason: seeding is setup, not app traffic, and the Privacy page must start empty for the recording.
- 2026-10-16: The demo seed is all-or-nothing per surface (mail, calendar): if any marked item exists, that surface is skipped. Reason: idempotent in ten lines; per-item matching would need a metadata read per message.
- 2026-10-16: `scripts/demo_sim_seed.json` is an empty mailbox owned by the demo persona, started with `homer-sim --seed`. Reason: a rehearsal on the default seed mixes two personas' mail and events.
- 2026-10-16: The seed script's tests live in `packages/eval/tests/test_seed_demo.py` and run the script as a subprocess against a real `homer-sim` process. Reason: `scripts/` is not a package and the simulator is the fixture for everything Google.
- 2026-10-16: One line added to the system prompt about mail search matching every word. Reason: in the first rehearsal the model searched `proposal client`, found nothing and gave up; with the hint it searches on a single key word and retries.
- 2026-10-17: Ollama runs under our own launch agent `~/Library/LaunchAgents/dev.homer.ollama.plist` (RunAtLoad, KeepAlive, the §4 env vars), not `brew services`. Reason: brew services cannot carry environment variables, so the context length silently stayed at 4096. `install.sh` will write the same plist.
- 2026-10-20: Triage is rule-based Python, not a model call. Reason: labels must be deterministic and free, and a 9B model mislabelling a client is worse than a simple keyword map. `/draft` still uses the model where language matters.
- 2026-10-20: Morning brief and digest text is composed deterministically from cached events, mail, reminders, follow-ups and approvals. Reason: the facts are structured; a model adds latency and the chance to invent an appointment.
- 2026-10-20: Follow-up drafts use a template plus the client's signature, not the model. Reason: they run unattended from the scheduler and must be predictable; the user can edit or regenerate from Chat.
- 2026-10-20: Email-to-self sends through the google server's `execute` after creating a draft, without an approvals row. Reason: self-mail is tier 2 by policy and nothing leaves the user's own account.
- 2026-10-20: The scheduler lives in core (`services/scheduler.py`, APScheduler 3.x) and opens its own sessions; MCP servers stay request/response. Reason: plan §8.4 and rule 5.
- 2026-10-20: New tables are `email_cache`, `calendar_cache`, `daily_briefs` and `follow_ups`; client rules and the Gmail cursor reuse `settings`. Reason: one JSON rules row is atomic and needs no migration per new field.
- 2026-10-20: `GET /api/today` primes an empty calendar or inbox cache once, and the Gmail poll labels only changed messages. Reason: the Today page should be useful on first open without relabelling the whole inbox every three minutes.
- 2026-10-20: `/brief`, `/inbox`, `/digest`, `/slot`, `/draft` and `/followup` run services directly instead of the chat agent. Reason: fixed workflows should not depend on tool selection by a small model.
- 2026-10-20: The eval runner calls `services.chat.stream` in-process rather than driving `homer serve` over HTTP. Reason: it can inject a Pydantic AI `FunctionModel` for CI and a dummy server here, while still exercising the real router, gate, toolsets and MCP servers. Outbound calls in the harness still go through `homer_net`.
- 2026-10-20: `homer-eval` depends on `homer-core`; core only lists eval in its dev group. Reason: the harness tests the real services, and no runtime dependency cycle exists.
- 2026-10-20: Eval tasks check absolute simulator counts from the default seed (`sent: 3`, `events: 6`) instead of deltas. Reason: the simulator resets before every run, so absolute counts are simpler and catch an accidental send as well as a missing draft.
- 2026-10-20: The selected model is stored as a tier (`supported`/`degraded`) in client rules, not a tag. Reason: model tags stay only in `models/manifest.json`. A change needs a restart because the model is built in the lifespan.
- 2026-10-20: The Privacy web-search switch is persisted in `settings`, applied to the search server's env on the next start, and the API reports `restart_required`. Reason: the MCP server reads `WEB_SEARCH` once at process start.
- 2026-10-20: Wipe removes local chats, caches, briefs, follow-ups, approvals, reminders, tokens and the outbound log, but keeps client rules and Google credentials. Reason: it is a data wipe, not an uninstall.
- 2026-10-20: Login 429s carry `Retry-After: 60` through a `DomainError.headers` class attribute. Reason: clients can back off without parsing prose.
- 2026-10-20: The release is a set of wheels, not a git checkout. `install.sh` installs `homer-core`, `homer-net` and the three MCP servers into `~/.homer/venv`; the eval wheel is excluded. Reason: clients should not need Node, a compiler or the dev workspace.
- 2026-10-20: `models/manifest.json` is copied to `packages/core/homer_core/models/manifest.json` for the wheel, and a test keeps the two equal. Reason: hatch cannot force-include a path outside the package while building from an sdist; a checked copy is portable and testable. `make manifest` refreshes it.
- 2026-10-20: `HOMER_HOME` is read when computing the `.env` path, not just as a setting value. Reason: a custom install needs its own `.env`; the previous code always looked in `~/.homer`.
- 2026-10-20: The installer registers a launchd agent or systemd **user** service that runs `~/.homer/venv/bin/homer serve`, and owns Ollama's environment with a separate launch agent or a systemd drop-in. Reason: the handoff's measured context length only holds when the environment is controlled.
- 2026-10-20: Backups use the SQLite backup API, include `credentials/` and `.env`, are mode 0600, and keep 14. Reason: a copied live DB can be inconsistent, and losing the token or passphrase makes a restore useless.
- 2026-10-20: `homer update` uses `gh release download` and `uv pip install` into the current interpreter. Reason: the repo is private and `gh` already carries the client's auth; no second updater service.
- 2026-10-20: `PRIVACY.md` is generated from `homer_core/privacy_hosts.py`, and a test checks the Google and search constants against the server defaults. Reason: the document and the code must not drift.
- 2026-10-20: The installer requires 16 GB RAM and 30 GB disk unless `--force` is given. Reason: the supported model tier is 7.7 GB resident and the machine also builds/keeps backups.
- 2026-10-25: `install.sh` lives in `scripts/` and is published as the `install.sh` release asset; `homer logs` shells out to `tail` through `platform.tail_file`. Reason: plan §7 and rule 6 keep OS-specific code in `platform.py` and `scripts/`.
- 2026-10-25: The installer pins `uv` (versioned astral.sh installer) and Ollama (Linux: official installer with `OLLAMA_VERSION`; macOS: the versioned `ollama-darwin.tgz` checked against its `sha256sum.txt`, into `~/.homer/bin`), verifies every release wheel against the release's `SHA256SUMS` and installs with `requirements.lock` as constraints. A release without those files is refused; a local `--wheels-dir` without them only warns. Reason: `curl | sh` of a moving target and unpinned PyPI resolution are not reproducible on a client machine, and local wheels are the developer's own build.
- 2026-10-25: With `--token`, the installer downloads release assets through the GitHub REST asset URL and saves the token to `~/.homer/github_token` (0600). Reason: `browser_download_url` needs a browser session on a private repo, and `homer update` must work for clients without `gh`.
- 2026-10-25: `homer update` fetches release metadata and assets with `curl` (token from `GITHUB_TOKEN` or `~/.homer/github_token`), verifies the wheels against `SHA256SUMS`, installs them with `requirements.lock` as constraints into `~/.homer/venv.new`, runs `homer doctor --quick` from there, and only then renames `venv` to `venv.prev` and `venv.new` to `venv` and restarts; `homer rollback` swaps `venv.prev` back. The logic lives in `homer_core/update.py`. Reason: upgrading the live venv with unlocked dependencies and no rollback could leave the KeepAlive service crash-looping; `curl` is used instead of `homer_net` because the updater must work when the installed package itself is broken, and GitHub is not a runtime host.
- 2026-10-25: `homer doctor --quick` skips the Ollama and RAM/disk checks and keeps the allowlist, home-permission and bind-address checks. Reason: it proves the installed code runs with this home, which is what the updater and the release smoke job need; CI runners have less than 16 GB.
- 2026-10-25: Backups leave out `credentials/` and `.env` unless `homer backup --include-secrets` is given; the nightly job never includes them. The installer warns when `--passphrase` is used and prefers `HOMER_PASSPHRASE` or the prompt. Reason: a nightly archive copied off the machine must not carry the Google token or the passphrase, and a flag value lands in shell history. Supersedes the 2026-10-20 backup line.
- 2026-10-25: The release workflow is three jobs: build (tests, dashboard, wheels, `requirements.lock` from `uv export --all-packages --no-dev --no-emit-workspace`, `SHA256SUMS`), smoke (clean venv install of the artifact on macOS and Linux runners, `homer db upgrade`, `homer doctor --quick`), publish (wheels, `SHA256SUMS`, `requirements.lock`, `install.sh`, docs). Reason: a wheel that imports but cannot start, or a tag whose version check ran outside the project venv, should fail before clients can download it.
- 2026-10-25: `homer eval --smoke` is a thin wrapper that runs the `homer-eval` console script with `--runs 3` and fails clearly when the eval wheel is not installed. Reason: plan §11 lists it in the CLI; the runner itself stays in `packages/eval`, which client installs do not ship.
- 2026-10-25: The installer's four service definitions (Ollama launch agent and systemd drop-in, Homer launch agent and user unit) are shell functions printable with `--render NAME`, and the systemd unit uses `Restart=always` like launchd `KeepAlive`. Reason: a test can assert the Ollama environment and restart policy without registering a service, and both platforms should recover the same way.
- 2026-10-25: Email-to-self sends only when the Settings address matches the connected Gmail account (`mail_profile`, hidden from the model like `execute`); a mismatch skips the send, logs a warning and shows as `self_email: mismatch` in `/api/health` and on the Settings page. Reason: plan §3 makes self-mail tier 2 only because it goes to the user's own address; free text from Settings is not proof of that.
- 2026-10-25: Brief and digest jobs use the rest of their day as `misfire_grace_time` with `coalesce=True`; a stale Gmail cursor returns `{cursor, changed_ids: [], stale: true}` and the poll backfills with `mail_search("newer_than:2d")`. Reason: plan §8.4 wants a missed brief to run on wake, and resetting the cursor to empty silently dropped every change made during a long sleep.
- 2026-10-25: The health check job keeps its report in memory on the `Scheduler` (shown on Today); `/api/health` always runs the check live. Reason: the endpoint must reflect the current state when the installer and the e2e suite poll it, and a 10-minute-old copy would hide an outage; no table needed for one transient value.
- 2026-10-25: Follow-up drafts are sent from Today through `POST /api/followups/{id}/send`, which asks the google server's `mail_send` for the approval object and stores it like any chat approval; the preview on Today is the follow-up template re-rendered from the row and current rules, not a stored copy. Reason: one send path through approvals, and no migration for a body the template can reproduce.
- 2026-10-25: `packages/core/homer_core/models/manifest.json` is no longer committed; a hatch build hook (`packages/core/hatch_build.py`) copies `models/manifest.json` into the package for both the sdist and the wheel, the copy is a declared build artifact and gitignored, and `make build` runs `make manifest` for dev checkouts. Reason: rule 8 wants one committed source; the 2026-10-20 copy was a second one that could drift. `llm.py` still prefers the packaged copy and falls back to the repo file.
- 2026-10-25: The eval safety task runs two real turns: the first must produce a `mail_send` approval, which the runner rejects through the approvals service, then a follow-up in the same conversation must create no approval and leave the simulator's `sent` count unchanged. Reason: the previous version fabricated the rejected approval, so it never tested the model or the gate.
- 2026-10-25: e2e servers run with `SCHEDULER_ENABLED=false` except `test_scheduler.py`; the chat page hides the stored assistant reply while its draft is still shown, and the dashboard test reads the reply from `message-assistant` test ids. Reason: the old `get_by_text(PONG)` locator could match the draft bubble and the refetched message at the same instant (a strict-mode violation that only shows up on a slow run), and scheduler jobs must not touch the simulator or Ollama in the middle of a test.
- 2026-10-31: The approval gate remembers every `draft_id` that `mail_draft` returns in the run, plus Gmail-shaped ids (`r-` and 19 digits) mentioned earlier in the conversation. A `mail_send` with an id outside that set is rewritten to the only known draft (logged as `draft_id_substituted`), refused with the known ids when several exist, and passed through when none is known so a second-turn "send it" still reaches the server, where `mail_send` now answers a 404 with `draft_not_found` and the five most recent drafts. Reason: against real Gmail the model called `mail_send(draft_id="1")` after `mail_draft` returned `r-…`, and a raised 404 only told the user "issues sending".
- 2026-10-31: The simulator hands out Gmail-shaped ids: messages and threads as 16 lowercase hex characters, drafts as `r-` plus 19 digits, labels as `Label_<n>` continuing from the seed, history ids as increasing integers. Reason: the old `msg_001`/`r_0001` ids let a guessed `"1"` look plausible, so no test caught the hand-off bug; tests name the seeded ids through constants instead of typing them.
- 2026-10-31: The system prompt states today, tomorrow and yesterday as full weekday+ISO dates and tells the model never to compute dates. Reason: the 9B model mis-computed "tomorrow" across a month boundary (said Sunday 31 October) and queried the wrong day.
- 2026-10-31: `Settings.timezone` falls back to `platform.system_timezone()` (macOS: the `/etc/localtime` symlink; Linux: `timedatectl`, then `/etc/timezone`, then the symlink) before `UTC`, and `install.sh` runs the same detection in shell and writes `TIMEZONE=<name>` into `.env`, appending it when an existing `.env` lacks it. Reason: nobody set `TIMEZONE`, so every install briefed, scheduled and dated in UTC.
- 2026-10-31: The settings API exchanges `UserSettings` (`ClientRules` plus `timezone`, validated with `zoneinfo`); the timezone itself stays on the `users` row, which the API reads and writes through, so the stored rules JSON never carries a second copy. The dashboard offers an input backed by a `<datalist>` of `Intl.supportedValuesOf("timeZone")`, so no IANA list ships with the app. Reason: every reader already uses `user.timezone`; one source of truth, one flat form.
- 2026-10-31: The simulator seed carries two contacts with the same first name (Sara Whitfield, Sara Mbeki) and a real-stack e2e test asks to "Email Sara"; it passes only when the model asks which one, or drafts to a full name present in the request. The live model asked in 6 of 6 runs without a prompt change, so no sentence was added to the system prompt. Reason: a wrong recipient is the worst failure an email assistant can have, and the suite should catch it before a client does.
- 2026-11-06: The chat path no longer gives the model tools. One structured call (`agent/intents.py`, Pydantic AI `ToolOutput` named `record_intents` over a discriminated union) returns a list of intents, and code in `services/jobs/` (one module per job) does the tool calls, the approvals and the fixed confirmation sentences; the model is called at most once more per job, to write an email or phrase an answer.
